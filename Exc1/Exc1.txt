Проблемы и инициативы:
●	В список сотрудников необходимо набрать SRE инженера, который сможет закрыть сразу несколько дыр: разбирать инциденты от клиентов, настроить мониторинг, логирование и трейсинг, заниматься инфраструктурой.
●	RabbitMQ - Если сообщение будет потеряно или очередь будет перегружена, это может привести к задержкам в выполнении заказов или несвоевременной реакции системы на изменения.
●	Отсутствие балансировки влияет на прямую на пользователя, поэтому для распределения нагрузки между Shop API и CRM API можно использовать API Gateway.
●	Общая База Данных для Shop и CRM требует разделения, так как не соответствует правилам микросервисов (один сервис - одна БД). Это может привести к большим проблемам, если например плохо настроены уровни транзакции.
●	Отсутствие кэша. Также может привезти к тому, что базе будет больно. Если еще учитывать предыдущий пункт, то с возрастающей нагрузкой приклад явно упадет.
●	Отсутвие автодеплоя на прод. Мануальное вмешательство в любом случае усложняет процесс наката и может привезти к ошибке по “человеческому фактору”.
●	Реализация undo для заявок (rollback, retry, переход из статуса в статус)
●	Отсутствие наблюдаемости.

Приоритет:
1.	Улучшение стратегии мониторинга и логирования для обнаружения потенциальных проблем с производительностью на ранних стадиях. (работа для SRE)
2.	Внедрение балансировки нагрузки для Shop API и CRM API, так как это напрямую влияет на взаимодействие с пользователями. (2 недели)
3.	Настройка автоматизации CI/CD. (работа для девопса)
4.	Подключение Redis для Shop API. (2 недели)
5.	Разделение баз данных. (3 недели)
6.	Оптимизация работы с очередями сообщений (RabbitMQ) для уменьшения возможных задержек в обработке заказов. (1 неделя)
7.	Разработка механизмов отказоустойчивости и восстановления для ключевых компонентов системы (например переходы из одного статуса в другой или retry). (2 недели)
