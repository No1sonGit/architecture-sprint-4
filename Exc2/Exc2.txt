Мотивация
Мониторинг нужно было внедрить на начальном этапе, ведь он мог бы предотвратить многие из тех проблем, с которыми компания сталкивается сегодня. Благодаря раннему обнаружению сбоев компания сможет оперативно реагировать на возникающие сложности, что позволит минимизировать количество просроченных заказов и, самое главное, значительно снизить количество жалоб со стороны клиентов. Кроме того, мониторинг значительно сократит время, затрачиваемое на ручной анализ и диагностику неполадок.
Система мониторинга дает возможность отслеживать ключевые показатели производительности, что позволит эффективнее планировать ресурсы и оптимизировать работу критически важных компонентов. Это станет особенно актуально при увеличении объема заказов, помогая избежать сбоев и поддерживать высокое качество обслуживания.
Кроме того, бизнес-метрики, которые будут собираться с помощью мониторинга, помогут отслеживать рост продаж или выявлять застойные моменты. Это откроет новые возможности для анализа и совершенствования работы компании, делая её более конкурентоспособной и устойчивой к вызовам растущего спроса.
Выбор подхода к мониторингу

Для мониторинга системы будем использовать разные подходы.

RED:
Этот подход будет полезен для мониторинга API.
●	Rate - будем отслеживать частоту вызовов API для отслеживания нагрузки;
●	Errors - процент неудачных запросов или ошибок, чтобы вовремя реагировать на проблемы с интеграцией;
●	Duration - задержку ответа на запросы, чтобы убедиться, что система работает быстро и без задержек.

USE:
Этот подход подойдет для мониторинга инфраструктуры (серверы, базы данных, RabbitMQ)
●	Utilization - мониторинг использования CPU, памяти и дискового пространства серверов;
●	Saturation - наблюдение за очередями запросов или насыщением ресурсов (например, переполнением очередей RabbitMQ);
●	Errors - количество ошибок в работе инфраструктуры.

Четыре золотых сигнала:
Этот подход будет использоваться для мониторинга MES и CRM.
●	Latency - мониторинг времени отклика ключевых систем (например, как быстро MES рассчитывает стоимость);
●	Traffic - измерение нагрузки на систему (например, количество обрабатываемых заказов);
●	Errors - отслеживание сбоев и исключений в процессе работы систем;
●	Saturation - оценка того, насколько близка система к своим пределам производительности.

Выбор метрик
В RabbitMQ нужно следить за количеством неуспешных сообщений (dead-letter-exchange) и сообщений, находящихся в обработке, чтобы оперативно выявлять узкие места в системе обмена данными.
Важными показателями для API интернет-магазина, CRM и MES являются количество запросов (RPS), использование CPU и памяти, а также время отклика (latency) для оценки производительности и предотвращения перегрузок.
Для баз данных интернет-магазина и MES важны метрики использования памяти и размера, чтобы избежать переполнения и поддерживать стабильную работу.
Также необходимо добавить метрики отвечающие за количество соединений для отслеживания состояния подключений, проверки соединений и анализа распределения по кластеру.
Необходимо отслеживать количество успешных и ошибочных запросов (HTTP 200 и 500) для всех API, что позволит контролировать стабильность работы системы.
Также важно учитывать количество активных сессий и объем трафика для оценки текущей нагрузки и пропускной способности системы.

План действий
Создание инстансов для мониторинга и сбора метрик:
●	Развернуть time-series базу данных (например, Prometheus) для хранения и обработки метрик.
●	Настроить Grafana или аналогичный инструмент для визуализации данных и построения дашбордов.
Настройка сбора метрик с сервисов:
●	Внедрить мониторинг для RabbitMQ: настроить сбор метрик dead-letter-exchange сообщений, сообщений в обработке.
●	Настроить экспорт метрик для API интернет-магазина, CRM и MES (RPS, время отклика, использование ресурсов).
●	Настроить сбор данных о памяти, размерах баз данных и количестве подключений для баз данных интернет-магазина и MES.
Конфигурация системы алертинга:
●	Настроить правила оповещений на основе критических метрик (высокая загрузка CPU, медленное время отклика, количество ошибок HTTP 500, превышение предела сообщений в RabbitMQ).
●	Настроить каналы уведомлений (я предпочитаю телеграм) для своевременного информирования команды о проблемах.
Оптимизация работы RabbitMQ:
●	Настроить мониторинг производительности RabbitMQ: следить за состоянием очередей и количеством сообщений в полете.
●	Внедрить мониторинг dead-letter сообщений для предотвращения накопления сообщений с ошибками.
Создание дашбордов для бизнес-метрик:
●	Настроить дашборды для отслеживания бизнес-показателей (рост заказов, просроченные заказы, активность API пользователей) на основе данных из CRM и MES.
●	Визуализировать основные ключевые метрики для быстрого анализа состояния системы в реальном времени.
